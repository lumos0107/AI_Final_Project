# 2라운드: GPT

## 1. 다른 검토자 의견에 대한 동의와 반박

- **교수:** A 유지, 이메일 귀속 수정, 소급 문서화 표시, 병합 마감 신설에 동의한다. 다만 “문서 6개는 커밋 1건 분량”이라는 평가는 검토자의 판단이다. 실제 담당 교수의 감점 기준으로 받아들일 수는 없다. 공지는 커밋 개수보다 내용·기간 분포·이슈와 PR 기록을 명시한다(원자료 2장).
- **엔지니어:** 이메일·작성자·리뷰 대기가 브랜치 수보다 급하다는 진단에 동의한다. 다만 “누구의 기여로도 잡히지 않는다”는 표현은 **학생 계정에 해당 커밋이 연결되지 않았다**로 좁혀야 한다. 이슈·PR 기록은 별개이며, 리뷰의 프로필 기여 반영도 조건부다(진행자 확인; 교수 1R 출처 1). release 자동삭제의 이중 PR 영향은 본인도 미확인했으므로 확정 근거에서 제외한다.
- **팀원:** 판단 주체 명시, PR #3의 리뷰 범위 지정, 담당자와 리뷰 응답 기한 도입에 동의한다. 다만 저장소 기록 0으로 실제 참여도 0을 단정할 수는 없다. Approve는 확인과 수정 반영이 끝난 뒤 제출해야 한다. 날짜 분산을 위한 재작성 금지는 타당하지만, 개인정보 정정을 위한 제한적 재작성은 별도로 판단한다.

## 2. 쟁점별 최종 입장

1) **브랜치 구성:** A를 유지한다. 첨부에서 이를 뒤집을 구체적인 필요는 없다. C의 `spike/`와 12/17 기능 동결을 가져오고, 주차 태그·최종 Release는 선택으로 둔다. develop·release 브랜치와 기본 브랜치 변경은 도입하지 않는다.

2) **버린 시험 코드:** 전부 main에 합칠 의무는 없다. 질문·실험자·방법·결과·탈락 이유는 문서로 남기고, 재현에 필요한 최소 코드만 `experiments/`에 선별 병합한다. 미병합 코드 커밋의 기본 브랜치 기여 집계는 기대하지 않는다(교수 1R 출처 1·3).

3) **squash를 끈 이유:** “작업 단위와 원래 커밋 이력을 보존하고 PR 리뷰와 연결하기 위해”로 고친다. 커밋 수 가산은 공지에 없으며, Contributors 그래프는 merge commit을 제외한다(원자료 2장; 엔지니어 1R 출처 4·5).

4) **마감:** 운영 기준은 **12/20 23:59까지 main 병합 완료**로 둔다. 내부 목표는 12/19 코드 PR 제출, 12/20 18:00 병합·검증 완료, 22:00 `v1.0`이다. 실제 교수의 시각·병합 판정과 시간대는 확인 필요다(공지; 교수 1R §5).

5) **소급 문서화·PR #3:** “11/17~19 활동을 11/19에 소급 정리”라고 명시하고 날짜를 분산하지 않는다. 이번 PR은 유지하되 요약·02·04·05의 사실과 판단 주체를 우선 리뷰하고, AI 원문은 참고 부록으로 구분한다. 전 파일의 공개 가능 여부는 확인한다.

6) **팀원 기여:** 초대·이메일 확인 후 #4의 운영 규칙, #3의 실제 참여·발언을 직접 리뷰한다. 분야 지도는 원저자·작성 시점을 확인하고, 팀원이 검증·보완한 내용을 본인 커밋으로 남긴다. “팀이”는 실제 발안자·결정자·검증자로 구체화한다.

7) **이메일:** 개인정보를 우선해 **(가)를 권고**한다. 정확한 계정 noreply 설정, 미병합 7개 커밋의 이메일 정정, 날짜 유지, force push 후 재리뷰·계정 연결 확인 순서다. (나)는 gmail 공개를 수용할 때 선택하며 기존 노출을 해소하지 않는다. 과거 공개 사본까지 회수되는지는 확인 필요다(진행자 확인).

8) **작성자·AI 표시:** 실제 작업과 검증에 책임지는 사람이 작성자다. Claude는 실제 사용 시 `Co-Authored-By`에 표시하고, PR에는 도구·사용 역할·사람의 검증 내용을 남긴다. 학생 공동저자는 실제 공동작업이 있을 때만 기재한다.

9) **1주차 확장 장치:** PR 양식 하나에 변경·검증·AI 사용과 오류를 담고, 이슈에는 목적·완료 조건·담당자를 적는다. 중복 라벨은 정리한다. 영역 라벨·CODEOWNERS는 보류하고, Actions는 반복 실행할 검사가 생길 때 도입한다.

## 3. 1라운드에서 고칠 내 주장

- **마감 후 문서 수정 위험의 지적 범위를 줄인다.** CONTRIBUTING 6장 2항은 이미 README·발표 자료로 정확히 한정했다. 직접 고칠 대상은 PR #4 요약의 “12/21부터 문서만”이라는 표현이다.
- **GitHub 조건의 불확실성을 해소한다.** 기본 브랜치 또는 gh-pages, 이메일에 따른 계정 연결, `user.name`이 연결 기준이 아니라는 점은 다른 검토자의 문서 확인을 받아들인다(교수 1R 출처 1; 엔지니어 1R 출처 3).
- **이메일 문제를 최우선에 추가한다.** 1라운드에서 놓친 학생 계정 귀속 실패와 개인 gmail 노출을 병합 전 해결 과제로 올린다. 이메일 비공개 설정 자체는 여전히 확인 필요다(진행자 확인).

## 4. 최종 우선순위

**지금 당장 — 최대 5개**

1. 사용자에게 이메일 방식 선택을 받아, 선택한 방식으로 정정하고 작성자·커미터 이메일 및 계정 연결을 확인한다.
2. 팀원을 초대하고 본인 계정에 연결되는 이메일과 리뷰 방법을 확인한다.
3. PR #3에 소급 정리 표시·판단 주체·리뷰 범위를 명시하고, AI 오류 주장에는 근거를 보완한다.
4. PR #4에 A 유지, 병합 마감, 작성자·AI 규칙, 기여 집계 설명을 반영한 뒤 두 PR을 실제 리뷰한다.
5. 주제 확정일과 두 사람의 사전 시험 담당·완료 조건을 정한다.

**1주차 안**

주제의 “본 적 없는 점” 한 문장, 핵심 시연과 성공 기준을 확정한다. 각자 사전 시험과 작은 PR을 수행하고, 분야 지도·참여 기록을 보완한다. PR 양식, 중복 라벨 정리, 리뷰 응답 목표 24시간, 코드 시작 전 `.gitignore`·`.env.example`을 마련한다.

**나중**

핵심 기능 구현과 함께 검증을 시작하고 반복 검사를 Actions로 옮긴다. 주차 태그는 필요할 때 남기며, 제출판의 커밋 식별자와 `v1.0`을 기록한다. 12/21부터는 공지가 허용한 README·발표 자료만 수정한다.
