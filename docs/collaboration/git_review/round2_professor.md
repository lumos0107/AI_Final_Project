기준 2026-11-19. 1라운드 네 편과 진행자 확인 사실을 읽었습니다. 새로 주장한 사실은 끝의 출처 번호나 명령 결과를 붙였습니다.

## 1. 다른 검토자 의견에 대한 동의와 반박

### 가. 엔지니어

- 동의
  1) 이메일은 PR #3·#4를 합치기 전에 고쳐야 합니다. main은 force push 금지라서(자료 5장 `allow_force_pushes:false`) 합친 뒤에는 되돌릴 수 없습니다.
  2) 보호 규칙이 두 사람에게 다르게 작동합니다. 내가 1라운드에서 놓친 점입니다. 보호 규칙은 기본적으로 관리자에게 적용되지 않습니다[1]. 교수 입장에서 더 걸리는 것은 주인 계정으로 도는 Claude Code도 같은 예외를 받는다는 점입니다. 사람이 리뷰하지 않은 AI 변경이 main에 들어갈 길이 열려 있습니다(직접 push까지 되는지는 시험하지 않아 확인 필요).
  3) 마감 기준은 '합치기 완료'여야 합니다. Activity 화면에 push와 병합 기록이 남는다는 근거는 내 1라운드 주장("날짜를 꾸미면 push 기록과 어긋난다")의 출처로 받겠습니다.
  4) 작성자는 사람, Claude는 `Co-Authored-By`에만 둡니다. 다른 저장소 커밋 일부(수 가림)가 Claude 작성이라는 조회 결과가 이 규칙을 문서로 남겨야 하는 이유입니다.
- 반박
  1) "PR 리뷰도 기여로 세니 팀원의 첫 기여로" 쓰자는 말은 절반만 맞습니다. 프로필 집계에서 리뷰는 'sometimes count'입니다[2]. 나는 Approve만 누른 리뷰를 기여로 보지 않습니다. 줄 코멘트나 수정 요청이 있어야 합니다.
  2) enforce_admins는 '선택'이 아닙니다. 팀원이 합류한 뒤 켜는 쪽을 권합니다.

### 나. 팀원

- 동의
  1) 문서의 "팀이"를 사람 이름(머리글자)으로 바꾸자는 의견에 동의합니다. 발표 필수 요소인 '역할 분담'과 동료평가에 바로 걸리는데 내가 놓쳤습니다.
  2) PR #3 리뷰 범위를 적어 두기, 리뷰 응답 24시간, 코드 전에 `.gitignore`(공개 저장소)에도 동의합니다.
- 반박
  1) "누가" 칸에 실제로 참여하지 않은 판단까지 팀원 이름을 넣으면 안 됩니다. 11/17~19가 한 사람과 AI의 작업이었다면 그대로 적는 편이 낫습니다. 팀원 몫은 앞으로 할 일(분야 지도, 사전 시험)로 쌓으면 됩니다.
  2) 이슈 양식 2개는 1주차에 필요 없습니다. PR 양식 하나로 충분합니다.

### 다. GPT

- 동의
  1) 마감 뒤 예외는 공지 문구대로 "README와 발표 자료"뿐입니다. CONTRIBUTING 6장 2)의 "`docs/` 브랜치와 PR로"는 범위를 넓게 읽게 만듭니다. 용어 정리집을 고르면 용어 데이터 파일은 기능의 일부입니다. 내 1라운드 문구도 같은 잘못이 있어 3장에서 고칩니다.
  2) squash를 끈 이유는 커밋 수가 아니라 기록 보존으로 적어야 합니다.
  3) 리뷰를 문서 PR(사실관계·공개 범위)과 기능 PR(실행)로 나누자는 의견에 동의합니다. 큰 기능을 나눈 중간 PR에는 `Refs #n`을 쓰고 마지막 PR만 `Closes`로 닫자는 의견도 같습니다.
  4) 깃 구성보다 주제, 한 문장 정의, 성공 기준이 급하고, AI 심사 점수가 그것을 입증하지 않는다는 데 동의합니다.
- 반박
  1) GPT는 도구 없이 써서 가장 큰 문제(커밋이 계정에 연결 안 됨)를 보지 못했습니다.
  2) GPT가 상으로 둔 '마감 예외 범위'는 12월에 터지는 문제입니다. 지금 순위는 이메일과 팀원 다음입니다.

## 2. 쟁점별 최종 입장

1) **브랜치**: A로 갑니다. 반대 근거는 남지 않았습니다. C에서는 `spike/`와 기능 동결 규칙(12/17부터 feat 안 받음)만 가져옵니다. 주차 태그는 선택으로 두고 규칙에 넣지 않습니다. Release는 `v1.0` 하나만 만듭니다. develop, release 브랜치, 기본 브랜치 변경은 하지 않습니다.
2) **버린 사전 시험**: 결과 문서(`06_pretest.md`)는 반드시 main에 합칩니다. 코드는 합칠 의무가 없습니다. 작고 재현 방법이 있으면 `experiments/`에 합칩니다. 그렇지 않으면 PR을 닫은 채 결과 문서에서 링크합니다. 나는 닫힌 PR도 기록으로 봅니다.
3) **squash를 끈 이유**: "작업 날짜와 단위, 리뷰 이력을 보존하려고"로 적습니다. squash는 여러 날 작업을 합친 날 하나로 바꿔 분포 증거를 지웁니다. "커밋 수" 표현은 지우고, merge commit은 Contributors 그래프에 잡히지 않는다[3]는 점도 한 줄 넣습니다.
4) **마감**: 기준은 "12/20 23:59까지 main에 합치기 완료"입니다. 내부 마감은 다음과 같습니다.
   - 기능 PR: 12/16에 합치기 끝(4주차 끝, 마일스톤의 동결과 맞춤)
   - fix PR: 12/20 20:00에 합치기 끝
   - `v1.0` 태그: 12/20 21:00
   - 12/21부터: README와 발표 자료만
5) **소급 문서화**: PR #3 본문 첫 줄에 "11/17~19 활동을 11/19에 정리해 올림"을 넣습니다. 날짜와 커밋 구성은 바꾸지 않습니다. PR은 쪼개지 않습니다. 대신 리뷰 범위를 README·04·05와 공개 여부로 좁히고, `blind_review/`는 "AI 출력 원문, 리뷰 제외"로 표시합니다.
6) **팀원 기여 0**: 다음 순서로 풉니다.
   - 초대하고 팀원 이메일을 확인합니다.
   - 팀원이 PR #4를 리뷰하고(줄 코멘트 포함), 이어서 PR #3을 정한 범위만 리뷰합니다.
   - 팀원이 자기 분야 지도를 자기 커밋으로 올립니다.
   - 사전 시험 하나를 팀원이 맡습니다.
   - "팀이"는 실제 참여자 이름으로 바꿉니다.
7) **이메일**: (가)를 권합니다.
   - 확실성: (나)는 문서에 "Old commits might not be linked"라고 적혀 있습니다[4]. noreply 주소는 c81c2b3에서 연결이 이미 확인됐고, 합치기 전에 API로 결과를 다시 볼 수 있습니다.
   - 노출: gmail이 main 기록에 영구히 들어가지 않습니다. 다만 완전히 가려지지는 않습니다. 옛 커밋은 PR 기록과 캐시로 남을 수 있습니다[5]. 다른 공개 저장소에도 gmail 커밋이 이미 있습니다(다른 저장소 visibility public, 엔지니어 조회, 수 가림).
   - 할 일: 작성자뿐 아니라 커미터 주소도 gmail이니(`git log --format=%ce`) 둘 다 바꿉니다. 작성 날짜는 유지합니다(정확한 명령은 확인 필요). PR에는 "작성자 메일 수정으로 force push" 한 줄을 남깁니다. (나)는 다른 저장소 연결 문제로 따로 정합니다.
8) **작성자와 AI 표시**: 작성자는 작업을 지시하고 결과를 확인한 사람입니다. Claude는 `Co-Authored-By` 줄에만 둡니다. PR 본문의 AI 표시는 유지합니다. 리뷰 코멘트와 결정 댓글은 사람이 직접 씁니다. AI가 쓴 리뷰는 리뷰로 보지 않습니다.
9) **1주차 확장 장치**
   - 넣을 것: PR 양식 1개(칸은 무엇을 했나 / AI를 어떻게 썼고 어디서 틀렸나 / 어떻게 확인했나), `.gitignore`와 `.env.example`, 라벨 중복 정리, 팀원 합류 뒤 enforce_admins 켜기
   - 넣지 않을 것: 이슈 양식, 영역 라벨, CODEOWNERS
   - Actions: 첫 테스트가 생길 때 함께
