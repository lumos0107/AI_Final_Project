# 1라운드: GPT

## 1. 지금까지 한 일 평가

**잘한 점**

- **평가에 필요한 근거를 남길 틀을 만들었다.** 후보를 버린 이유, AI 판단을 사람이 수정한 기록, 이슈·PR을 연결한 구성은 공지의 ‘AI 활용 과정’, ‘도전과 해결’, ‘이슈와 PR 기록’에 대응한다(2장, 4장). 다만 첨부에는 개별 문서 전문이 없으므로, 기록의 정확성과 구체성까지 검증된 것은 아니다.
- **기본 협업 흐름이 단순하다.** 이슈 → 짧은 작업 브랜치 → 상대 리뷰 → main 병합은 두 사람이 작업 이유와 변경 내용을 추적하기 좋은 구성이다(3장). 실제로 이슈 #1·#2와 PR #3·#4가 연결되어 있다(5장).
- **일정에 완성도 확보 시간을 배정했다.** 2주차의 ‘핵심 기능 하나가 처음부터 끝까지 동작’, 마감 주의 ‘새 기능 없이 버그만’은 범위를 통제하는 데 유용하다(3장). README 실행 방법과 테스트도 일정에 포함했다.

**문제점**

- **[상] 마감 이후 허용 범위를 넓게 적었다.** 공지는 **README와 깃허브에 올라간 발표 자료**만 예외로 명시한다(2장). 그런데 PR #4는 “12/21부터 문서만”, CONTRIBUTING은 `docs/` 브랜치 사용으로 요약한다(3·5장). 이것을 모든 Markdown·문서 수정 허용으로 읽으면 위험하다. 특히 용어 정리집을 선택한다면 ‘용어 설명 데이터’가 서비스 기능을 구성할 수 있으므로, 문서라는 이름만으로 예외라고 판단해서는 안 된다. 허용 범위는 확인 필요다.

- **[상] 평가 대응 문서보다 주제와 검증 목표의 확정이 급하다.** 현재 기록은 여러 차례 후보 생성과 AI 심사를 설명하지만, 주제는 미정이다(1·4장). 공지의 핵심은 팀이 정의한 ‘본 적 없는 것’과 결과물이 얼마나 맞아떨어지는지다(2장). **AI 심사 점수와 검색 기록은 그 일치나 실제 사용자 관심을 대신 입증하지 않는다.** 다음 산출물은 추가 후보 목록보다 ‘한 문장 정의, 핵심 사용 장면, 성공 판단 기준’이어야 한다.

- **[상] 사람별 책임과 승인 체계가 아직 작동하지 않는다.** 참여자는 저장소 주인 한 명이고 PR은 모두 리뷰 전이며, 관리자는 보호 규칙의 예외다(1·5장). 따라서 현재는 ‘상대 승인 후 병합’이라는 규칙만 있고 운영 실적은 없다. 또한 AI가 작성한 문서의 “팀이 판단했다”는 표현은 실제 결정자와 참여자가 확인해야 한다(4장). `Co-Authored-By: Claude`는 AI 사용을 밝히지만, 두 학생의 판단·구현·검증 책임을 구분해 주지는 않는다.

- **[중] 커밋 수 보존을 개인 평가와 지나치게 연결했다.** squash를 끈 이유가 “각자의 커밋 기록이 줄어들기 때문”이라고 명시되어 있다(3장). 그러나 공지는 커밋된 **코드 내용**, 기간 전체의 작업 분포, 이슈·PR 기록을 본다고 했지 커밋 개수에 비례해 점수를 준다고 하지 않았다(2장). merge commit 유지 자체는 가능하지만, 설명은 ‘작업 단위와 검토 이력을 보존한다’로 바꾸는 편이 적절하다.

- **[중] 소급 문서화와 당시 작업 기록을 구분해야 한다.** 11/17부터의 과정을 11/19 17:00에 여섯 커밋으로 정리했다(4·5장). 이는 정리 방식으로는 가능하지만, 여러 날에 고르게 작업했다는 증거가 되지는 않는다. 반대로 같은 시각이라는 이유만으로 실제 활동이 없었다고 판단할 수도 없다. ‘11/17~19 활동을 11/19에 정리’라고 명시하고, 앞으로 실제 작업 시점에 기록하면 된다. 날짜를 인위적으로 분산할 이유는 없다.

- **[중] 리뷰 규칙이 변경 성격과 맞지 않는 부분이 있다.** 모든 리뷰에서 브랜치를 받아 실행하도록 하지만, 현재 두 PR은 문서다(3·5장). 문서는 사실관계·링크·공개 범위를, 기능은 실행 결과를 검토하도록 나누는 편이 실용적이다. PR #3은 요약 문서와 AI 심사 원문까지 포함하므로, “10분 안”이라는 목표보다 **어떤 주장과 결정을 누가 확인할지**를 정하는 것이 중요하다(3·4장).

## 2. 브랜치 구성 권고

**후보 A를 유지하고, 사전 시험과 마감 운영만 보완하는 안을 권한다.**

후보 B는 영구 브랜치 두 개와 여러 보조 브랜치를 관리해야 한다. 후보 C도 기본 브랜치 변경, 주간 develop → main PR, release의 양쪽 병합, 마감 후 기본 브랜치 복구가 추가된다(6장). 현재 자료에는 이 추가 절차가 해결해야 할 구체적인 병렬 개발·배포 문제가 제시되어 있지 않다. 두 명이 다른 수업과 병행하는 상황에서는 준수할 절차부터 줄이는 편이 맞다(1장).

구체적으로는 다음과 같이 운영한다.

1. **main과 짧은 작업 브랜치를 유지한다.** PR #3·#4의 대상도 main으로 둔다. 아직 코드가 없는 지금은 main의 기준을 ‘검토된 기획·설정이 있는 상태’로 해석하고, 실행물이 생기면 ‘합의한 실행·검증 절차를 통과한 상태’로 구체화한다.
2. **사전 시험에는 필요할 때만 `spike/`를 쓴다.** 시험마다 확인할 질문과 종료 조건을 먼저 정한다. 버린 후보는 결과·실패 이유·필요한 재현 근거를 남기되, 탈락한 실험 코드를 전부 main에 합칠 의무는 두지 않는다. 후보 C의 ‘버린 후보도 develop에 합친다’는 규칙은 목적에 비해 강하다(6장).
3. **merge commit은 유지해도 된다.** 다만 문서 하나당 커밋 하나처럼 형식에 맞추기보다, 나중에 변경 이유를 설명할 수 있는 단위로 나눈다.
4. **12/17부터 main에서 기능 추가를 멈추고 수정·검증한다.** 두 사람이 새 기능을 계속 개발할 계획이 없다면 제출용 release 브랜치를 별도로 둘 필요는 약하다. 코드 관련 PR의 병합과 최종 검증까지 마감 전에 끝내고, 제출 커밋 식별자와 태그를 기록한다.
5. **주간 마일스톤은 유지하되 버전·Release 발행을 의무화하지 않는다.** ‘주제 확정’도 중요한 진척이지만 매주 소프트웨어 판을 발행해야 할 근거는 없다. 발표 문서 수정만으로 `v1.1`을 반드시 만들 필요도 없다(6장).

## 3. 확장성

**브랜치 구조는 충분하다. 후보 C의 관리 장치는 현재 단계에는 지나친 부분이 있고, 실제 검증 기준은 부족하다.**

기능이 늘어난다는 이유만으로 영구 브랜치를 늘릴 필요는 없다. 우선 필요한 것은 작업 범위, 완료 조건, 변경 간 의존관계를 설명하는 이슈다.

- **‘기능 하나 = 이슈 하나 = 브랜치 하나’는 원칙으로 고정하지 않는다.** 큰 기능은 여러 PR로 나눌 수 있다. 이 경우 모든 PR에 `Closes`를 붙이면 완료 전에 이슈가 닫힐 수 있으므로, 중간 PR은 관련 이슈를 참조하고 완료 PR에서 닫도록 규칙을 보완한다(3·6장).
- **양식은 작은 것부터 시작한다.** 이슈에는 목적·완료 조건·담당자, PR에는 변경 내용·검증 결과 정도면 출발할 수 있다. 기능·버그·시험·AI 실수 양식 네 종류를 지금 모두 만드는 일은 우선순위가 낮다(6장).
- **영역 라벨과 CODEOWNERS는 실제 구분 필요가 생기면 도입한다.** 아직 주제와 기술 구조가 미정이므로 `area:mcp-skill` 같은 영역을 먼저 확정할 근거가 없다(1·6장).
- **테스트는 3주차까지 미루지 않는다.** 1주차에 성공 조건을 정하고, 2주차 핵심 기능 구현과 함께 최소 검증을 수행해야 한다. 기술이 정해진 뒤 반복 가치가 큰 실행·빌드·핵심 동작 검사를 자동화하면 된다. Skill·MCP 역시 해결할 문제와 사용 이유부터 정해야 한다(2·3장).

## 4. 우선순위

**지금 당장**

- 팀원을 초대하고 숙련도·작업 가능 시간을 확인한다. 두 사람이 PR #3의 사실관계와 PR #4의 규칙에 동의한 뒤 병합한다.
- 마감 이후 허용 대상을 공지 문구대로 고친다. ‘문서 브랜치이면 허용’이라는 해석을 없앤다.
- 커밋 수 중심의 설명을 수정하고, 소급 문서화 날짜와 실제 결정자를 분명히 한다.
- 관리자 예외의 용도를 합의한다. 초대·초기 설정이 끝난 뒤에도 우회가 상시 경로가 되지 않도록 한다.

**1주차(~11/25) 안**

- 주제를 결정하고 ‘본 적 없는 점 한 문장’, 핵심 시연 한 장면, 성공 기준, 포기할 기능을 작성한다.
- 두 사람이 맡을 구현·검증 범위를 정한다. 커밋 수를 맞추는 방식보다 각자 맡은 결과와 판단을 설명할 수 있게 한다.
- 가장 불확실한 기술 또는 사용자 가치부터 짧게 시험한다.
- README에 현재 상태와 실행 방법의 뼈대를 만들고, 핵심 기능의 최소 검증 절차를 정한다.
- 마감 전에 완료할 검증·병합·제출판 기록 절차를 합의한다.

**나중**

- 반복 작업이 확인되면 CI, 추가 양식, 영역 라벨을 도입한다.
- 인원이나 책임 영역이 실제로 늘어나면 CODEOWNERS를 검토한다.
- 동시에 유지해야 할 제품 버전이 생길 때 release 브랜치를 재검토한다.

## 5. 확인 필요

- **평가 방식:** 문서 기여·AI 보조 코드·커밋 작성자와 실제 작업자를 교수자가 어떻게 평가하는지, 기여 그래프를 직접 집계 기준으로 쓰는지 확인 필요. 공지에는 세부 산식이 없다.
- **기록의 사실성:** 팀원도 후보 선정과 수정 판단에 참여했는지, AI가 작성한 발언·판단 요약과 검색 근거가 정확한지 확인 필요. 첨부만으로 독창성이나 유사 서비스 부재를 확정할 수 없다.
- **GitHub 설명:** “main에 들어간 커밋만”, `user.name`은 “깃허브 아이디”라는 안내의 정확한 조건은 확인 필요(3장). 특히 후보 C는 기본 브랜치를 develop으로 바꾸므로 기존 설명과의 정합성 확인이 필요하다.
- **보호 설정:** 승인 뒤 추가 변경이 생겼을 때 재검토를 요구하는지 등, 제시되지 않은 보호 옵션은 확인 필요(5장).
- **마감 판정:** 적용 시간대와 커밋·push·병합 중 무엇을 기준으로 판단하는지, 서비스 콘텐츠 데이터와 README 외 문서의 수정 허용 범위는 확인 필요. 확인 전에는 코드 관련 작업을 병합까지 마감 전에 완료하는 일정으로 운영하는 것이 타당하다.
