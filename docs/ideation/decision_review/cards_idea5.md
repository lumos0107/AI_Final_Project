# 아이디어 5 평가에 쓴 카드

아이디어 5는 16개 평가 뒤에 들어와서 같은 심사위원 3명이 따로 채점했습니다. 다듬을 때마다 새 카드로 다시 채점했습니다.

## 카드 17. 누구나 쓰는 개인화 AI 비서

- 대상: LLM을 쓰기 어려워하는 일반 사용자(고령층만이 아니라 20대 포함)
- 무엇을 하나: 메일·일정·파일 활동을 지식 그래프(사람, 파일, 활동, 시간을 관계로 이은 기억)로 쌓아 두고, "다음 주 회의 잡고 길동이한테 알려 줘"처럼 막연하게 말하면 기억에서 맥락을 찾은 뒤, MCP로 연결한 여러 앱 기능(예: 일정 추가, 메일 초안) 가운데 필요한 것을 AI가 골라 이어서 실행하고, 어떤 기억을 근거로 판단했는지 보여 준다. 먼 방향은 폰에 LLM 하나를 두고 앱 기능을 MCP 단위로 통일해 사용자가 필요한 기능 조합을 직접 만들어 쓰는 "앱 없는 스마트폰"이다.
- 이미 있는 것(웹 검색 요약): 피클(Pickle, 사용자마다 기억을 쌓는 개인 AI 에이전트가 연결한 캘린더·메일·외부 서비스로 일정 확인, 식당 예약, 매장 전화를 대신 함, 2026.11 국내 앱스토어 무료 앱 상위권, 말하지 않은 가족 관계를 추론하거나 시키지 않은 전화를 건 일로 개인정보 논란), 구글 Gemini(일부 안드로이드 앱에서 여러 단계 작업 대행, 앱이 AppFunctions로 기능을 기능 단위로 공개), 애플 Siri AI(개인 맥락, 앱 기능 연결), 도이치텔레콤 AI Phone(앱 대신 비서가 일 처리), Nothing Playground(프롬프트로 위젯 미니 앱 만들기), ChatGPT·Claude의 메일·일정 연결 기능.

## 카드 18. 앱 기능 조립 (카드 17을 고친 안)

- 대상: 앱을 찾고 익히기 어려운 일반 사용자(고령층만이 아니라 LLM·스마트폰 앱에 서툰 20대 포함)
- 무엇을 하나: 앱을 통째로 깔아 쓰는 대신, 여러 앱의 기능(사진 보내기, 전화, 일정 추가, 메시지 등)을 기능 단위로 쪼개 MCP라는 하나의 공개 표준으로 내놓는다. 사용자가 "엄마한테 연락하는 앱 만들어 줘"처럼 말하면 LLM이 필요한 기능만 골라 묶은 작은 앱(화면 포함)을 바로 만들어 주고, 사용자는 그 앱을 홈 화면에 두고 계속 쓴다. 먼 방향은 폰에 LLM 하나를 두고 기능만 MCP로 통일해 사용자가 필요한 앱을 직접 만들어 쓰는 "앱 없는 스마트폰"이다. 4주 범위: 가짜 앱 3개(메시지, 사진, 일정)의 기능을 MCP 서버로 쪼개 두고, 말 한마디로 그 기능들을 묶은 작은 앱 화면을 만들어 실행하는 것까지.
- 이미 있는 것(웹 검색 요약): iOS 27 단축어(2026.6, 원하는 자동화를 말로 설명하면 여러 앱 동작을 엮은 단축어를 만들어 줌. 결과는 화면 없는 자동화이고 애플 기기 안에서만), 구글 Create My Widget(2026.5, 말로 설명하면 Gemini가 캘린더·메일 등 데이터를 엮은 위젯을 만듦. 위젯만), 구글 AppFunctions(안드로이드 앱이 기능을 기능 단위로 내놓고 Gemini가 씀), Nothing Essential Apps/Playground(프롬프트로 위젯 미니 앱 만들기, 2026.2 베타, 지금은 위젯만이고 새 앱 게시는 잠시 멈춤), MCP Apps(2026.1 MCP 공식 확장, 앱 회사가 만든 화면을 ChatGPT·Claude 대화 안에 띄움. 사용자가 기능을 조립하는 것은 아님), 피클·Gemini·Siri AI(기억을 바탕으로 앱 기능을 대신 실행하는 비서).

## 카드 19. 요청 중심 기능 분해 (카드 17, 18을 다시 고친 안)

- 대상: LLM 취약계층. 원하는 일을 말로 요청할 수는 있지만, 그 요청을 AI로 끝까지 해내지 못하는 사람(고령층만이 아니라 AI 활용이 서툰 20대 포함)
- 무엇을 하나: 기존 서비스들은 앱이 가진 기능을 쪼개 AI에 내놓지만(아래에서 위로), 이 서비스는 거꾸로 "사용자가 진짜 원하는 요청"에서 출발한다(위에서 아래로). 의도와 맥락이 담긴 요청은 앞단(피클 같은 비서, 상용 서비스)이 만든 것을 그대로 받고, 이 서비스는 그 요청을 끝까지 구현하는 데 필요한 기능 단위로 나눈다. 나눈 기능은 생활 기능 분류표(예: 연락하기 > 사진 보내기, 일정 > 추가하기)라는 중간 단계로 표현되고, 각 칸에 여러 회사의 기존 MCP·API 기능을 통째로 또는 일부만 잇는다. 기존 MCP에 없는 기능은 직접 만들어 덧붙인다. 실행 전에는 중간 단계(어떤 기능을 어떤 순서로, 받는 사람은 누구인지, 되돌릴 수 없는 일인지)를 쉬운 말로 보여 주고 확인받는다. 프로그래밍으로 치면 자연어 요청(초고수준)과 실제 API 호출(저수준) 사이의 중간 언어를 만드는 것이다.
- 4주 범위: 연락·사진·일정 한 영역의 기능 분류표를 만들고, 기존 MCP를 칸에 연결하고, 기존 MCP에 없는 기능 1~2개를 덧붙인다. 실제 요청 모음 N개에 대해 "기존 MCP만으로 구현된 비율"과 "덧붙인 기능까지 넣었을 때 구현된 비율", "실행 전 확인으로 막은 잘못된 실행 수"를 잰다.
- 이미 있는 것(웹 검색 요약): Zapier MCP(9,000개 넘는 앱의 동작 가운데 원하는 것만 골라 하나의 MCP 서버로 내놓고, 칸 값을 고정해 일부만 쓸 수 있음. 개발자·관리자가 설정), MCP 게이트웨이(Kong, Orq.ai 등. 여러 MCP 서버의 도구를 모아 일부만 내놓음), 구글 AppFunctions(앱이 기능 단위로 내놓고 Gemini가 씀), 애플 App Intents 스키마 도메인(메일·사진 등 애플이 정한 분야별 동작 틀에 앱이 맞춰 들어옴. 애플 기기 안에서만), schema.org Action(웹용 동작 분류. 실행과는 안 이어짐), MCP 도구 분류 연구(JSPLIT 등. 개발자 쪽에서 도구 고르기를 돕는 분류. 표준 분류는 아직 없음), Cloudflare Code Mode(MCP 도구를 TypeScript API로 바꿔 LLM이 코드를 짜게 함. 토큰 절약용, 개발자용), 피클·Gemini·Siri AI(요청을 받아 앱 기능을 대신 실행하는 비서). 조사한 범위에서 "생활 요청 기준 기능 분류 + 여러 회사 MCP를 칸에 잇기 + 없는 기능 채우기 + 실행 전 확인"을 함께 하는 것은 찾지 못함.

## 카드 20. 요청에서 자라는 기능 분류표 (카드 19의 정의를 다듬은 안)

- 한 문장 정의: 애플 App Intents나 schema.org처럼 회사가 정한 분야 틀에 앱을 끼워 맞추는 것이 아니라, 사람들이 실제로 한 요청을 모아 거꾸로 뽑아낸 "생활 기능 분류표"를 만들고, 그 칸을 여러 회사의 MCP로 채우되 기존 MCP로 채워지지 않는 칸은 직접 만들어 채워서, 지금 AI 비서가 끝내지 못하는 요청을 끝까지 실현한다.
- 대상: LLM 취약계층. 원하는 일을 말로 요청할 수는 있지만, AI 비서가 중간에 "그건 할 수 없어요"로 멈추면 다른 방법을 찾지 못하는 사람(고령층만이 아니라 AI 활용이 서툰 20대 포함).
- 무엇이 다른가
  1) 분류표의 출발점: 회사가 미리 정한 분야(메일, 사진 등)가 아니라 실제 요청 모음. 새 요청이 들어와 기존 칸으로 설명되지 않으면 칸이 새로 생긴다(계속 자람).
  2) 빈 칸을 메운다: 기존 서비스는 앱이 내놓은 기능만 쓸 수 있다. 이 안은 분류표 칸마다 "기존 MCP로 됨 / 일부만 됨 / 안 됨"을 표시하고, 안 되는 칸은 기존 기능을 조합하거나 새 기능을 만들어 채운다. 예: "지난주 사진 중 엄마 나온 것만 골라 큰 글씨 설명과 함께 보내 줘"에서 "사람별로 사진 고르기", "큰 글씨 설명 붙이기"가 기존 MCP에 없으면 채운다.
  3) 보이는 결과: 사용자에게 이번 요청이 어떤 기능 칸들로 이뤄졌고, 그중 어느 칸이 새로 채워져서 가능해졌는지를 쉬운 말로 보여 주고, 되돌릴 수 없는 일은 확인받은 뒤 실행한다.
- 요청의 의도와 맥락을 알아듣는 부분은 앞단(피클 같은 비서, 상용 서비스)에 맡기고, 이 안은 그 뒤를 맡는다.
- 4주 범위와 잴 것: 연락·사진·일정 영역의 실제 요청 100개를 모아 분류표를 뽑고, 기존 MCP를 칸에 잇고, 빈 칸 2~3개를 채운다. 같은 요청 100개를 (가) 일반 AI 비서에 MCP를 연결한 경우, (나) 이 안으로 처리한 경우로 나눠 "끝까지 실현된 요청 수"를 비교하고, 새로 채운 칸 덕분에 처음 실현된 요청 수를 따로 센다.
- 이미 있는 것(웹 검색 요약): 애플 App Intents 스키마 도메인(애플이 정한 분야별 동작 틀, 애플 기기 안에서만), schema.org Action(웹용 동작 분류, 실행과는 안 이어짐), Zapier MCP·MCP 게이트웨이(여러 서비스 기능을 모아 일부만 내놓음, 개발자·관리자가 설정, 서비스에 없는 기능은 못 씀), 구글 AppFunctions(앱이 내놓은 기능을 Gemini가 씀), MCP 도구 분류 연구(JSPLIT, 마켓플레이스 도구 분류 등. 이미 있는 도구를 분류해 고르기를 도움), 에이전트 계획 연구(CGAP 등. 가진 기능 목록에 맞춰 요청을 계획), 실행 전 계획 확인(여러 에이전트 도구에 이미 흔함), 피클·Gemini·Siri AI(요청을 받아 연결된 기능으로 대신 실행). 조사한 범위에서 "실제 요청에서 자라는 분류표 + 칸별로 기존 MCP 가능 여부 표시 + 빈 칸을 만들어 채우기"를 함께 하는 것은 찾지 못함.
